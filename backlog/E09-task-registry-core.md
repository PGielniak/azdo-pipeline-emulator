# E09 — Task handler registry & core tasks (groups A/B)

Phase: P2 · Depends on: E04, E06 · Design: docs/03 §1–§2, groups A/B, §4
Primary grounding set: `microsoft/azure-pipelines-tasks` — for **every** handler: the task's `Tasks/<Name>V<n>/task.json` (inputs, defaults, aliases) **and** its implementation source (behavior), both commit-pinned · `microsoft/azure-pipelines-task-lib` `node/` (input conventions, match/find semantics) · per-task reference pages under learn.microsoft.com/azure/devops/pipelines/tasks/reference/.

Global rule: a handler task is not done until its research note contains an **input table** (name, alias, type, default, required) copied from the pinned `task.json` — never typed from memory — and each emitted behavior cites either the task source or its reference page.

## E09-S01 — As a converter developer, tasks normalize and emit through one plugin API, so adding a task never touches the engine.
Acceptance: registry + normalization per docs/03 §1–§2.

- [ ] **E09-S01-T01 — Handler API & registry**
  **Do:** `TaskHandler`/`EmittedStep` interfaces per docs/03 §1 **plus** `fidelityClaim: string` (claim ID) on emitted metadata (consumed by E07); registry keyed by `Name@major` and task GUID; resolution order (exact → user handler → stub).
  **Ground:** docs/03 §1 spec; GUID-reference support grounded in yaml-schema `steps-task` page (quote how tasks may be referenced).
  **Done:** registry unit tests; a sample handler registered end-to-end.
- [ ] **E09-S01-T02 — Input normalization from `task.json`**
  **Do:** defaults, alias resolution, required enforcement, type handling (`boolean` loose parse, `filePath` resolution base, `multiLine`, `pickList` validation, `connectedService:*` extraction); version-major selection.
  **Ground:** task.json schema knowledge from the tasks repo (locate the schema/contribution docs inside `microsoft/azure-pipelines-tasks` or the extension docs page learn.microsoft.com/azure/devops/extend/develop/integrate-build-task — pin whichever documents input types); boolean parse semantics from task-lib `node/task.ts` `getBoolInput` (pin exact code).
  **Done:** normalization tests against 4 vendored task.jsons incl. alias + default + bad-pickList cases.
- [ ] **E09-S01-T03 — `azdo_match` (minimatch runtime)**
  **Do:** bash implementation of the pattern subset (`**`, `*`, `?`, `!` negation lines, multi-pattern separators) with documented deltas for exotic patterns.
  **Ground:** task-lib `node/task.ts` `findMatch`/`match` + its default `MatchOptions` (pin — these defaults, e.g. `dot`, `nocase` per-OS, decide real behavior); minimatch library README for pattern semantics (pin).
  **Done:** bats conformance table generated by running the same patterns through actual task-lib `findMatch` in a Node harness (the harness output is the grounding artifact) — bash must match on the supported subset; unsupported patterns emit the documented warning.
- [ ] **E09-S01-T04 — Unknown-task stub + user handler drop-in**
  **Do:** stub emission (warning + resolved-inputs JSON dump + configurable result); drop-in lookup `handlers/<Name>@<major>`; invocation env `INPUT_*`/`ENDPOINT_*`/`SECRET_*` matching the real convention.
  **Ground:** task-lib `node/task.ts` `getInput` env-name encoding (pin the exact transform: spaces, dots, case) — the drop-in contract must byte-match it; endpoint env naming from task-lib endpoint accessors (pin).
  **Done:** bats: unknown task stubs per config; drop-in receives correctly-encoded env (asserted against the pinned transform).
