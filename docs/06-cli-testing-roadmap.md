## 1. CLI

```
azdo-emu auth login [--org URL] [--mode az|pat]   # reports which mode works; caches nothing
azdo-emu auth status [--github] [--org URL] [--mode interactive|az|pat]

azdo-emu convert <pipeline.yml> -o <dir>
    [--org URL --project NAME]            # context for @alias resolution, variable groups, schema
    [--parameter key=value]...            # runtime parameters (repeatable); complex via @file.json
    [--target-os linux|windows|macos]     # override pool inference
    [--checkout-mode clone|copy|worktree]
    [--exec-env host|sandbox]             # D9 (revised): default execution environment baked into the
                                          #   project. `host` is the default; `sandbox` is **deferred** and
                                          #   not implemented (E12-S02-T02, docs/04 §9)
    [--sandbox-image IMG]                 # override the default vmImage→image mapping (sandbox only; deferred with it)
    [--group-names | --no-group-names]    # list variable-group names in .env.example when signed in (values never fetched)
    [--frozen | --update [what]]          # lockfile behavior (docs/05 §4)
    [--offline]                           # make no network call — satisfiable only via `--frozen` over a warm
                                          #   expansion cache or `--offline-expand` (docs/05 §5); wiring is E10-S02-T01
    [--offline-expand]                    # E12-S01-T01: expand with the retained local engine instead of the
                                          #   service — a **degraded fallback** (PLAN D3, docs/07 §6). Off by
                                          #   default; the conversion it produces is labelled degraded and
                                          #   carries a warning. Writes no expansion cache/lock entry (docs/05 §4).
    [--only-stage NAME]...                # partial conversion for huge pipelines; a dependency on a stage
                                          #   left out is dropped with a warning (E10-S02-T01, §5 decision 69(a))
    [--strict]                            # exit 2 when the conversion produced any warning
    [--no-bundle]                         # send the pipeline as authored, without inlining local templates
                                          #   (E03-S06); the service then reads the committed files

azdo-emu doctor <outdir> [--sandbox]      # verify tool prereqs from manifest.json — on the host by default; `--sandbox`
                                          #   checks inside the sandbox image and is deferred with it (D9 revised)
azdo-emu fetch-artifacts <outdir> [--refresh|--latest]
azdo-emu run <outdir> [...]               # thin convenience proxy to <outdir>/run.sh (optional sugar)
```

> **`preview-diff` removed 2026-08-22 (E12-S03-T01, completing E03-S05-T02's demotion).** With the
> service *as* the expansion (PLAN D3) there is nothing to diff on the default path, so the command
> is gone from this surface and from `packages/cli/src/program.ts`. Its two jobs live on elsewhere:
> **service drift** → the nightly re-expansion harness (§3 L3, E11-S03-T01); **fallback parity** →
> conformance (§3 L2, E11-S02). The normalizer it was built on (E03-S05-T01) is unaffected.

Conventions: human-readable output with `--json` for tooling; exit codes 0 ok / 1 conversion errors / 2 warnings-as-errors (`--strict`). **CLI usage errors** (unknown flag, missing argument, unknown command) reuse **1** rather than adding a code outside that set — which is also the CLI library's own default, so the two never need translating (E10-S01-T01, C-E13-007). `convert` ends with a one-line summary of the warnings/unsupported list it wrote into the generated `README.md` (described in the closing paragraph of docs/04 §12 — the README has no section of its own there; flagged for E12-S03-T01).

> **Revised 2026-08-22 (E12-S02-T01).** Exit code `3` (below `--min-coverage`) and the flag itself are
> gone with the weighted coverage metric (PLAN D10 revised, docs/07 §6, docs/04 §13's banner);
> `EXIT` in `packages/cli/src/exit.ts` reserves `0/1/2`. C-E13-007's decision — usage errors reuse
> `1` — is unaffected by the set shrinking.

Implemented in `packages/cli` (E10-S01-T01): `src/exit.ts` owns the policy (`EXIT`, `CliError`, `NotImplementedError`), `src/program.ts` registers the surface above and returns an exit code instead of calling `process.exit`, and `src/bin.ts` is the only module that touches process state. Commands not yet implemented are *registered* and fail with a message naming the epic that implements them, so `--help` stays honest about the intended surface.

## 2. Config file — `azdo-emu.yaml` (next to the pipeline, all keys optional; CLI > config > defaults)

```yaml
organization: https://dev.azure.com/contoso
project: Platform
auth: { azdo: interactive, github: gh }          # interactive|az|pat / gh|pat
parameters: { deployEnv: dev }                    # default runtime parameters
repositories:                                     # alias overrides (docs/05 §3)
  templates: { path: ../pipeline-templates }      #   e.g. local working copy while editing templates
variableGroups: { listNames: true }               # names only — values are always user-filled in .env
tasks:
  unknown: stub                                   # stub|fail|prompt — fallback when a task can't run for real
  overrides: { "SonarQubePrepare@5": skip }       # per-task opt-out: skip|stub|fail
output:
  targetOs: linux
  checkoutMode: clone
  sharedWorkspace: true                           # D8 (revised): one shared workspace per run.
                                                  #   false = per-job isolation — deferred fidelity, not implemented
  execution:                                      # D9 (revised) sandbox — deferred (docs/04 §9)
    environment: host                             #   host|sandbox — host is the default; sandbox is not implemented yet
    image: null                                   #   override the default vmImage→image mapping (sandbox only)
    dockerSocket: auto                            #   auto|share|none — host-socket passthrough (sandbox only)
```

Implemented in `packages/cli/src/config/` (E10-S01-T02): discovery is **beside the pipeline file** (there is no `--config` flag in §1); parsing uses plain `yaml`, *not* the engine's pipeline parser, so the service quirks (anchors rejected, case-folded duplicate keys, single document — C-E01-021..028) deliberately do **not** apply to our own file format. Two rules §2 leaves open are settled in `research/E13-cli-config-doctor.md`: **map-valued keys merge per key** (`parameters`, `repositories`, `tasks.overrides`) while scalars and lists replace wholesale (C-E13-012), and **paths typed on the command line resolve from the working directory while paths written in the config resolve from the config file's own directory** (C-E13-013). The machine-readable schema is committed at `schema/azdo-emu.schema.json` (draft-07) for editor support via `# yaml-language-server: $schema=…`; a test pins it to the loader so the two cannot drift.

## 3. Testing strategy

| Layer | What | How |
|---|---|---|
| L1 Expression unit | Full function/coercion table (~300 cases from the expressions doc + oracle-resolved edge cases) | Table-driven; same tables run against **both** backends (eval + compiled-shell via bats) so the two can never diverge |
| L2 Expansion goldens | Fixture YAML in → expanded YAML out | Snapshot tests; fixtures include every directive, template type, parameter type, nesting patterns. **Re-scoped 2026-08-22 (E12-S03-T01):** on the default path the golden *is* the service's pinned `finalYaml` (`fixtures/oracle/`), so these snapshots now exercise the **offline fallback** and its agreement with that pin — conformance work (E11-S02), not a gate on the shipped conversion |
| L3 **Service drift** | The pinned `finalYaml` still matches what the service returns *today* | **Re-scoped 2026-08-22 (E12-S03-T01):** expansion parity is true by construction now (PLAN D3), so what is tested is drift, not agreement — nightly re-expansion of the corpus against the test org (E11-S03-T01, PAT in CI secret), normalized (E03-S05-T01) and diffed against `fixtures/oracle/`; a mismatch is **triaged** (E11-S03-T02), never auto-accepted, and becomes a fixture update plus, where the fallback disagrees too, an L2 case. `preview-diff` was the old vehicle and is gone (§1) |
> **CI interpreter (E11-S01-T03, 2026-08-23).** L4 runs on the version the runtime targets, **bash
> ≥ 4** (PLAN D2): `macos-latest` ships only bash 3.2.57 (C-E00-028), so the workflow installs a
> modern bash and puts Homebrew's bin ahead of `/bin` for the bats step (C-E00-029), with an
> explicit interpreter check in front of it — a missing bash 4 otherwise reads as ~30 runtime bugs
> (`bad substitution`) rather than as one environment fault. bats itself is happy on 3.2
> (C-E00-005), which is exactly why this needed saying out loud.

| L4 Runtime unit | `runtime.sh` behaviors: setvariable/isoutput propagation, prependpath, masking, macro edge cases (unmatched literal), conditions vs results, continueOnError/failOnStderr/retries, artifact flow, deps outputs across jobs/stages | bats-core; runs in CI on ubuntu + macos |
| L5 E2E | Convert & run sample apps (dotnet, node, python, docker) in containers approximating hosted images | Docker; assert artifacts produced, exit codes, key log lines |
| L6 Real-run parity spot checks (**the only layer that can validate what the oracle cannot see** — see the two limits below) | Same fixture pipeline run in real ADO and locally; compare artifact contents, produced variables, step result sequence | Manual-triggered CI job (costs real pipeline minutes); release gate for majors |

Repo layout of the runners (E11-S01-T01): L1/L2 run under **vitest projects** — one per TypeScript package (`cli`, `engine`, `emit`, `fetch`), plus `repo` for meta-tests about the test layout itself; each project keeps its suite in `packages/<pkg>/test/**/*.test.ts`, so `pnpm vitest run --project engine` runs one package. L4 runs under **bats** in `packages/runtime/test/`, with shared helpers in `test/helpers/*.bash` loaded via `load` (relative to the test file, no `BATS_LIB_PATH` to set) and a fixture store that copies `fixtures/runtime/<name>` into the test's own `BATS_TEST_TMPDIR` before the test may touch it. `pnpm test` = vitest (with coverage) + bats; CI runs the same two commands and uploads junit + coverage reports.

Coverage gating: thresholds live in the root `vitest.config.ts` (coverage is root-level in vitest — there is no per-project coverage config); "per package" is expressed as glob keys (`packages/cli/src/**`) plus a repo-wide floor, and the numbers are a **ratchet seeded from measured coverage**, never an aspiration — a threshold above reality would make the first CI run red for no defect. Global and per-package sets are checked independently, so a package number below the repo floor is a second, narrower gate rather than a weakening; the one legitimate way a number goes *down* is re-seeding a placeholder package from measurement once it gains real code (`emit` at P2). **Second legitimate case, added 2026-08-22 (owner decision, §5 entry 47): a repo-wide re-baseline after a merge brings in code the numbers were never measured against.** The rebase onto the parallel E03/E06 work did exactly that, and CI then failed on five consecutive pushes to `main` with every test green — a gate that is always red has stopped gating, because no reviewer can separate a regression from the standing failure. The re-seed is **symmetric and from measurement**: `packages/engine` came down to its real number, `cli` and `fetch` went up. It is not a licence to lower a number that a *diff* made red — that case is still "write the test". Two traps are guarded by `test/test-layout.test.ts` rather than by convention: a package that gains tests but no project (its suite silently never runs) and a threshold glob that stops matching (vitest reports *no* error for an unmatched glob — it just stops gating).

Corpus: ≥30 pipelines patterned after real-world shapes — nested cross-repo templates, `extends` + `each` over `jobList`, matrix builds, deployment jobs with runOnce/canary, multi-checkout, artifact hand-offs between stages, variable groups + runtime expressions, monorepo path-heavy pipelines. Grown continuously from bug reports (every bug → corpus entry first).

Corpus mechanics (E11-S01-T02): entries live at `fixtures/corpus/<entry>/` (`pipeline.yml`, optional `templates/*.yml`, a README naming what the entry exercises) and their oracle pairs at `fixtures/oracle/<entry>.final.yml`, with `MANIFEST.json` recording the input hash each pair was fetched for — so a fixture edited without re-verification is a red test (`test/corpus.test.ts`), not a stale golden. `fixtures/corpus/` **mirrors the oracle repository's `/corpus/` directory**, because the service resolves `template:` references against the repo, treating a `yamlOverride` as though it were the pipeline definition's own file: templates must be pushed before the preview call, root references spelled `/corpus/<entry>/…` and in-template references spelled as bare siblings (C-E12-011/012). Goldens are redacted, so every consumer of a fresh response — the `--update` flow, the nightly re-expansion (E11-S03-T01, which replaced `preview-diff`) — must redact before diffing.

Two limits of the oracle as an instrument, found by authoring corpus v1 and load-bearing for what L2/L3 may claim:

- **The oracle cannot see everything.** `strategy: matrix`/`parallel` is *not* expanded by the service (C-E12-018) — job multiplication happens at run time — so no golden can prove it; that behaviour is E04's, verified at L6. Variable-group contents are likewise never inlined (C-E12-016), which is independent confirmation of D5.
- **Some corpus shapes need org objects, not just YAML.** `environment:` and `- group:` are validated at *load* time and fail with "does not exist or has not been authorized" until the object exists **and** the pipeline is authorized for it (C-E12-015/017); `scripts/oracle-provision.ts` provisions the ones corpus v1 needs. The expansion also rewrites shortcut steps to task **GUIDs** (`checkout`/`download` GUIDs that the task catalogue itself cannot resolve — C-E12-019/020), which the E03-S05-T01 normalizer must canonicalize or the nightly re-expansion (E11-S03-T01) reports permanent false drift.

## 5. Decisions record & remaining open questions

Decided 2026-07-30 (with the user):
1. **Azure DevOps Server (on-prem): out of scope.**
2. **Task priority = the Azure/Kubernetes deployment set** — AzurePowerShell, PowerShell/Bash, Helm install/deploy, Docker build/push, Azure resource-group (ARM/Bicep) deployment, Kubernetes actions, Key Vault, storage-account operations → group D moved to P4, general toolchains to P5 (docs/03).
3. **Windows host: skipped for now, must remain addable** — emitter keeps a per-job target-OS backend seam; scheduled as the "Future" phase.
4. **Variable groups → `.env.example` only**, filled by the user (names listed when signed in; values never fetched).
5. ~~**Every conversion emits a coverage report** (docs/04 §13) with the `--min-coverage` gate.~~
   **Revised 2026-08-22 (E12-S02-T01):** every conversion emits a **warnings/unsupported list** in
   the generated `README.md` with per-step fidelity labels. No metric, no gate (PLAN D10, docs/07 §6).
6. **Grounding-source correction (2026-07-30, E00-S02-T02):** the C# expressions/object-templating engine sources are **not** in `microsoft/azure-pipelines-agent` (it consumes the closed `Microsoft.TeamFoundation.DistributedTask.Expressions` NuGet; conditions evaluated in `src/Agent.Worker/ExpressionManager.cs`). Open behavioral reference for E02/E03 is the `actions/runner` fork `src/Sdk/DTExpressions2`/`DTObjectTemplating`/`DTPipelines`, with the oracle (D6) outranking it on divergence. Corrected: PLAN §9, docs/02 intro, E02/E03 epic grounding sets, REFERENCES.md (claims C-E00-012/013).
7. **Isolated execution by default (D11)** — decided 2026-07-30 (user requirement: local debugging must run in a container-isolated environment): the generated project executes inside one long-lived sandbox container per run when a container runtime is available (`auto`; `--host` opts out), project bind-mounted at the identical absolute path so the same scripts run unchanged in both environments (D2 intact); docker-socket passthrough is opt-in for docker-using pipelines. Distinct from ADO `container:` jobs (E14-S02). Added: PLAN §5 D11, docs/04 §9, config `output.execution.*`, story E14-S04 (T01/T02 scheduled at P2 tail).

8. **Schema validation is a guided walk, and the docs outrank the vendored schema (2026-07-30, E01-S02-T01).** The vendored `service-schema.json` is not self-sufficient: acceptance depends on the VS Code-extension keywords (`firstProperty`/`ignoreCase`/`aliases`) and on pipeline values being strings, so a stock ajv run *rejects valid pipelines* (documented `target:` on task steps) and emits >1000 errors for a single mistyped key (C-E01-011, C-E01-019). Decided: implement the walk in `packages/engine/src/frontend/validate.ts` mirroring `microsoft/azure-pipelines-language-server` semantics; keep ajv only as the vendored-file integrity smoke test; carry doc-proven schema fixes as an explicit `DOCUMENTED_CORRECTIONS` list re-checked on every schema refresh; treat unknown tasks/inputs as warnings until the org schema lands (E01-S02-T03). Two behaviors are oracle-pending in `research/E01-yaml-frontend.md` (Q1 discriminator ordering — warning for now; Q2 unknown task inputs). Updated: docs/01 §1.

9. **Doc correction — `---` is a marker, not always a separator (2026-08-11, E01-S01-T02).** docs/01 §1 said "Only a single document per file; `---` separators rejected". The live service accepts a single document opened by a leading `---` and closed by a trailing `...` (both HTTP 200), and rejects only a *second* document (C-E01-025/024); reading the old wording literally would have produced false rejections on the very common `---`-prefixed pipeline file. Also corrected in the same pass: anchors are rejected on the **definition**, not on alias use, so the placeholder `ALIAS_UNSUPPORTED` error from E01-S01-T01 is replaced by `ANCHOR_UNSUPPORTED` (C-E01-022), and duplicate keys are reported at the second occurrence with the service's own wording and collide **case-insensitively even for user-chosen names** (C-E01-023/028) — the yaml package's `uniqueKeys` check is therefore turned off so our check owns the message. Updated: docs/01 §1; evidence `research/experiments/E01-quirks/`.

10. **The org schema replaces the vendored one wholesale, and falls back rather than failing (2026-08-11, E01-S02-T03).** The measured live `GET {org}/_apis/distributedtask/yamlschema` response is the *same generator's* document as the vendored snapshot (draft-07, same `$id`, all four VS Code keywords, identical 119 definitions; the one non-task divergence resolves to the same `{type: string}`) — so injection is a swap, not a merge, and nothing the walk relies on is lost (C-E01-030/032). Decided: gate an injected document on dialect + "uses no keyword the walk leaves unimplemented", and on failure **degrade to the vendored schema with recorded reasons** instead of erroring, since a surprising server response must not block a conversion; apply `DOCUMENTED_CORRECTIONS` to the org document too, because they patch the generator rather than our snapshot (C-E01-037); word the unknown-task hint by source, mirroring the service's own `validateTaskNames` semantics (C-E01-033). Fetch/cache stays E08-S03-T07, now with a measured cache policy (no bustable version, non-byte-stable body, `vso.agentpools` scope — C-E01-034/035/036). Updated: docs/01 §1, docs/05 §2 + §4; evidence `research/experiments/E01-orgschema/`.

    (c) **`copy` mode refuses `clean: true` instead of honoring it.** `git clean -ffdx` on a copied work tree deletes exactly the uncommitted changes that are the mode's entire reason to exist (docs/04 §8: "for testing uncommitted changes"). The two settings are individually reasonable and jointly incoherent, and the mode is the more local, more explicit choice — it comes from `--checkout-mode`, chosen for this run, while `clean` comes from a pipeline written for the hosted agent. Decided: report it as `degraded` and copy anyway. The fetch-shaped options (`fetchDepth`, `fetchTags`) are announced as no-ops in `copy` and `worktree` for the same reason: silence would read as support.

    (d) **The copy is made with `tar`, not `rsync`.** docs/04 §8 specified rsync; rsync is not present in this container and is not guaranteed in the images this project targets, while `tar` is POSIX and preserves modes, symlinks and hardlinks. A two-implementation fallback was rejected: the rsync arm could not be exercised by the suite here, and an untested branch in the one function that empties a directory is worse than a slightly slower copy.

    (e) **Local hardening with no upstream counterpart: the checkout target must resolve inside `$(Pipeline.Workspace)`.** On the agent, escaping the work directory needs an opt-in variable (C-E06-105); here it is simply refused, because `clean` runs `git clean -ffdx` and `copy` empties its target before writing — a `path:` that escaped the workspace would let a converted pipeline delete the user's own files. `Build.SourceBranch`/`SourceVersion`/`Repository.*` are **seeded, never overwritten**, so the `.env` override docs/04 §8 promises survives the checkout; `Build.SourceVersion` is additionally read *before* the checkout, so an override actually selects the commit rather than being recorded after the fact.

    (f) **Local *relaxation* with no upstream counterpart: `-c protocol.file.allow=always` on the submodule commands.** Since CVE-2022-39253 git refuses the `file` transport for submodule clones, and 40(b) makes the emulated origin a `file://` URL — so `submodules: true` fails outright with "transport 'file' not allowed" (C-E06-112, measured). The restriction is a consequence of the emulator's own decision, not an agent behavior to reproduce; the hosted agent's submodule URLs are https. Decided: relax it, scoped to `submodule sync`/`submodule update`, over repositories the user already has on local disk. `submodule foreach` clones nothing and is left alone. This is the one place in the checkout implementation that is deliberately *more* permissive than the host git default, so it is recorded here rather than buried in a comment.

41. **The multi-checkout signal is a per-job environment variable the emitter sets, and the two path variables are seeded from the agent's rules rather than from where the files went (2026-08-22, E06-S05-T03).** The layout rule — one checkout in a job puts sources in `s`, two or more put every repository including `self` in `s/<repoName>` — depends on a fact no single `checkout` step knows: how many checkout steps the job has. The agent has the same problem and solves it by computing `HasMultipleCheckouts` **once at job preparation** and handing the answer to the plugin that places the repository, the extension that seeds the variables and the directory manager (C-E06-115). Decided: mirror that shape exactly. The emitter, which knows the job's step list statically, exports `AZDO_HAS_MULTIPLE_CHECKOUTS` per job beside `AZDO_STATE_DIR`/`AZDO_SELF_REPO`, and `azdo_checkout` reads it. A counting API (`AZDO_CHECKOUT_COUNT`, or the runtime tallying the checkouts it has performed) was rejected: it implies the runtime derives the boolean, which would make the *first* checkout in a two-checkout job behave as a single checkout — the agent never has that ordering problem because the answer predates every step.

    (a) **`Build.SourcesDirectory` and `Build.Repository.LocalPath` do not point at the checkout.** Under multi-checkout `self`'s files are in `s/<repoName>` while both variables stay at `s` (C-E06-116/117); only a `path` that *differs* from the default moves `LocalPath`, and nothing moves `SourcesDirectory` off `s` unless the job has exactly one repository. This is deliberate agent backward-compatibility (their PR #3237), it is not stated on the doc page, and seeding either variable from the resolved checkout target — the obvious implementation, and what the single-checkout code did — produces a plausible wrong answer that no other test in the suite would catch. It is recorded here because a future reader will find the code counter-intuitive and "fix" it; the bats case names the surprise in its title for the same reason.

    (b) **The folder name is `RepositoryUtil.GetCloneDirectory`, ported rather than approximated.** It is git's own clone-directory algorithm and `basename` is not a substitute: it strips a scheme, skips past the *last* `@`, trims trailing slashes and one `.git`, takes the last `/`- then `:`-separated segment, and trims a trailing `:<digits>` port **only** when the name contained no slash (C-E06-118). The agent's own L0 table is ported wholesale as the conformance fixture, which is where the two invertible orderings are pinned. Two non-parity guards sit on top, because these names can come from a local directory basename rather than from the service: a name reducing to `.`, `..`, `/` or nothing is refused instead of resolved — `s/..` is the workspace, and `clean` deletes inside whatever the target resolves to — and the input that makes C# throw out of `Substring` (`x://`) is refused with that message instead of a bash arithmetic error.

    (c) **`workspaceRepo` stays with the emitter.** Picking the repository that retargets `System.DefaultWorkingDirectory` requires scanning the whole job's step list, which the agent does in job preparation, before any checkout runs (C-E06-120). `azdo_checkout` accepts the option and reports it as not emulated here, the same treatment `fetchFilter`/`persistCredentials` got in decision 40; E05 sets the variable at job setup. Non-`self` checkouts likewise seed no `Build.*` variables at all — that family describes the triggering repository, which in a converted pipeline is always `self` (C-E06-121) — and they never fall back to `AZDO_SELF_REPO` for their source, because a green run holding the wrong repository's files is worse than a failure.

    (d) **The blocked half of the task's Ground field did not block the task.** It asked for one ambiguous combination (`self` + `path` + a second repo) to be settled by a real run; this environment has no oracle credentials. It did not need one: the combination is ambiguous only in the doc page, and the agent answers it exactly, in one named method per variable (`RepositoryPlugin.GetRepoPath`, `BuildJobExtension.GetDefaultRepoLocalPathValue`, `BuildDirectoryManager.UpdateDirectory`). BACKLOG §3 ranks agent source above docs for runtime behavior, so the source that *would have produced* the run's result was read instead of the result being observed.

54. **A mechanical inliner cannot bundle a *parameterized* template, and the failure is silent — so the bundler refuses rather than splices (2026-08-23, E03-S06-T02).** docs/02 §5.1 specifies the bundler as "a mechanical inliner, not an expander — it never evaluates `${{ }}`, never resolves a directive, and never binds a parameter", and E03-S06-T02's **Do** says to "inline the file's content" with no caveat. Twelve live probes (`research/experiments/E03-bundle/`, C-E03-408..413) show that specification is only equivalent for part of the input space, and the part it is wrong about is the common one.

    (a) **What was measured.** Six shapes, each submitted twice — once referencing the committed file, once with the bytes a mechanical splice produces — compared on the *normalized* expansion. Parameterless includes are **normalized-identical** (C-E03-408), so are nested ones (C-E03-409), and so is a template that *declares* `parameters:` but never reads one (C-E03-410) — the trigger is reading, not declaring, which widens the sound subset materially. A template that reads `${{ parameters.* }}` is **HTTP 400 `Key not found 'greeting'`** when the parent does not declare that name (C-E03-411) — the splice necessarily drops the template's own `parameters:` block, which is not legal inside a `steps:` list, so the reference resolves against the parent's table, and decision 19(c)'s `parameters`-raises-on-miss rule does the rest.

    (b) **The claim that decided the design is C-E03-412: when the parent *does* declare the same name, both halves return 200 and the expansions differ** — committed gives the leaf's `echo leaf-default`, inlined gives the root's `echo root-value`. That is a pipeline that converts, runs, and quietly does the wrong thing. So the service cannot be relied on to police this: a bundler that spliced optimistically would be correct, loudly broken, or silently wrong depending on a name collision it has no reason to inspect. Decided: **inline iff the file reads no `${{ parameters.* }}`** (C-E03-413), enforced in `packages/engine/src/template/inline.ts` by a deliberately conservative *text* scan rather than an expression parse — the safe answer to a spelling we fail to parse is "yes, it might read one", and a parser bug must not become a silent mis-inline. A refused reference is left in the override and reported as a **warning**: the expansion is still correct, it just reads the committed file, so the user's local edit is invisible. That is degraded, not broken, and the warning says so.

    (c) **This is a scope boundary of the simplification, not an oversight of the task.** Making local edits to a parameterized template visible requires substituting the parameter values at the splice — which is *binding*, which is the service's job under PLAN **D3**. The bundler cannot do it without becoming the expander D3 exists to avoid. So E03-S06-T02 stays `[!]`: its Done criterion ("a two-file pipeline with a nested template converts with no `@self` references left in the override") is met and tested for the parameterless shapes and cannot be met for the parameterized ones. **E03-S06-T05** is filed at the end of the story to decide what the product does about them — the options are a documented limitation, `--offline-expand`'s local engine (which *does* bind), or a `templateParameters` round-trip — and picking one is a design decision, not this task's to make silently. docs/02 §5.1's bundler table is corrected in the same diff, since as written it would have had T02 build exactly the splice that is silently wrong.

    (d) **Two smaller boundaries recorded with it, both reported rather than attempted.** `extends:` is a document-shape replacement rather than a list splice, and an `extends` target is parameterized by construction, so it would land on (b) anyway. A reference inside a `parameters:` **value** (E03-S06-T01's `parameters` site) is only reached once the receiving template inserts the list, so inlining it means predicting that insertion. Both are warned about by code `bundle-template-site-unsupported`, and both fold into E03-S06-T05.

55. **`templateParameters` is a root-only field, which closes one of E03-S06-T05's three options before it is opened (2026-08-23, E03-S06-T03).** Decision 54 left three candidate answers for parameterized local templates, the third being "a `templateParameters` round-trip that lets the service bind while still seeing local bytes — establish by probe whether any request shape permits it." Probed: **it does not.** A root pipeline with no `parameters:` that includes a template declaring `greeting`, sent with `templateParameters: {greeting: …}`, is rejected HTTP 400 `"Unexpected parameter 'greeting'"` (C-E03-418). The field validates against the **root** `parameters:` block only; a template's parameters are bound from the YAML, where they are written. So E03-S06-T05 chooses between a documented limitation and routing to `--offline-expand`, and does not need to spend oracle budget on option (c).

    (a) **The task's own `Do` was wrong in the same way, and is corrected rather than quietly satisfied.** It reads "pass `templateParameters` (and `parameters:` at the `extends` boundary) through to the expansion call … as the `templateParameters` request field". Reference-level and `extends`-level `parameters:` are not request fields at all — they are YAML the service reads in place, which is why E03-S06-T02's `passed-committed` transcript shows a `- template:` + `parameters:` expanding to the supplied value with **no client plumbing**. The task's Done criterion is therefore met by measurement rather than by code, and the code this task did add serves the *other*, real use of the field: supplying values for the root pipeline's own runtime parameters.

    (b) **A latent cache collision was fixed here because this task is what would have triggered it.** `expansionRequestHash` hashed the `yamlOverride` alone, so two conversions of one pipeline with different parameter values shared a cache entry and a lockfile pin — the second would silently read the first's `finalYaml`. Nothing exercised it before, because nothing set the field. The hash now covers a canonical, key-sorted composite; a request with **no** parameters still hashes to the override alone, so warm caches and committed lock entries stay valid and only the new ground is new.

    (c) **Three wire rules recorded for whoever builds the CLI surface (E10-S02-T01).** An undeclared name is rejected, not ignored (C-E03-415), so names cannot be passed through speculatively. Values are coerced to the declared type and a string is accepted for every scalar, so the client's `Record<string, string>` typing is narrower than the service needs but never wrong (C-E03-416). A structured value must be **serialized JSON**, not a raw JSON object — the raw form fails with a server-side `ArgumentNullException` naming `runParameters`, which carries no line/col and no remediation, while the JSON string binds and parses back into a real object (C-E03-417). That last one is what makes `--parameter name=@file.json` reachable, and `serializeTemplateParameters` is where it is applied.

56. **A canceled run exits non-zero, which corrects docs/04 §3's "iff `Failed`" rather than reading it (2026-08-23, E06-S06-T02).** docs/04 §3 said "run exit code is non-zero iff the pipeline result is `Failed`". Implemented literally, a run the user interrupted with Ctrl-C would exit **0** and report success to whatever invoked `run.sh` — a CI wrapper, a git hook, a shell `&&` chain. The sentence is not defending that outcome; it is enumerating the three *job* results the paragraph above it lists (`Succeeded`, `SucceededWithIssues`, `Failed`) and never considers `Canceled`, which is a step/run state the five-value vocabulary carries (`azdo__valid_step_result`) and which `azdo__job_status_from_results` already ranks **above** `Failed`. Decided: `azdo_run_exit_code` returns non-zero for `Failed` **and** `Canceled`; docs/04 §3 is corrected in the same diff (rule 5). Three notes.

    (a) **One exit code, not two.** The contract docs/04 states is "non-zero", and both states get `1`. A distinct code for `Canceled` (130 is the shell convention for SIGINT) would be a convention nothing else in the project reads — the CLI's own policy is `0/1/2` with `2` reserved for usage (C-E13-007, decision 43(b)) — and inventing a fourth value here would put the generated project and the converter on different scales. If a caller ever needs to tell the two apart, `azdo_run_result` prints the state by name.

    (b) **The aggregate reads step results, not per-level rollups.** `azdo_run_result` folds every file under `state/results/**` with the same worst-wins ranking `azdo__job_status_from_results` uses within one job (C-E06-059..061), skipping the `issues/` sidecars that share the tree. Re-aggregating stage-by-stage would be the same fold over a partition of the same set, and a job whose `continueOnError` degraded a `Failed` to `SucceededWithIssues` has already had that written into its step results — so the flat fold is not a shortcut, it is the same answer with fewer places to disagree.

    (c) **The summary table is ours, and is grounded in the design docs rather than in a pinned source.** docs/04 §2 asks for an "End-of-run summary table (step, result, duration, log path), mirroring the ADO UI's job view". The agent reports to the service, not to a shell, so there is no agent behavior to copy and no claim to record — stated here so a later reader does not go looking for one. Records live in `state/summary/` rather than beside the per-step results, because the table spans every stage and job while `state/results/<stage>/<job>/` is scoped to one job; they are numbered in completion order, which is sound while execution is sequential (docs/04 §3; `--parallel` is deferred to the archived P6) and would need a non-racing ordering key if that changes. One field per line, following the state store's file-per-value reasoning: a `displayName` may contain any character a YAML scalar may, and a delimited row would have to quote it.

60. **The generated-project naming rules are ours, decided once and tested against the corpus (2026-08-24, E05-S01-T01).** The service has no filesystem to copy, so every path/slug/numbering rule in the scaffolder is an internal spec (docs/04 §1), not Azure DevOps behavior — the same reason E04-S03-T04 and E06-S06-T02 recorded no claim, and the "validated against real pipelines" half of the task's Ground field is met by snapshotting the `stages/` tree of all ten corpus entries built from the captured `final.yml`s. Four rules, each pinned by a test:

    (a) **`slugify` lower-cases and collapses every run of non-`[a-z0-9]` to a single `-`, then trims leading/trailing `-`, returning `''` for symbol-only input.** Lower-casing is deliberate: two names differing only in case would collide on a case-insensitive filesystem, and this repo has already been bitten by exactly that (C-E03-204). The fallback chain is `displayName` → the node id → a kind token (`stage`/`job`/`step`), because a stage or job id may be the empty string (C-E04-004) and a step's displayName may slug to `''`.

    (b) **A stage/step is numbered by its 1-based ordinal within its parent, ×10, zero-padded to three** (`010`, `020`, …) so gaps are left for hand-inserted debugging steps. A **job** is numbered by its *group's* ordinal instead: a matrix/`parallel:` job is one authored job the model expands into several `Job`s sharing a `referenceName` (C-E04-136), so the legs share one number and differ only by suffix — numbering each leg would misread the matrix as several authored jobs.

    (c) **A matrix leg or `parallel:` slice appends `__<suffix>` to the job directory** — docs/04 §1's `010-BuildJob__linux_x64/` — the suffix slugged like any other name, with slug-colliding suffixes disambiguated by `-2`/`-3`/… (e.g. `linux_debug`/`linux-debug` → `__linux-debug`/`__linux-debug-2`). A matrix leg carries its key in `matrixKey` (C-E04-110); a `parallel:` slice has no `matrixKey`, so its position is recovered from the `id` suffix the strategy expansion appended (`<referenceName> <position>`, C-E04-121). The base job of an empty or runtime-expression matrix is indistinguishable from a plain job (`id === referenceName`) and gets no suffix.

    (d) **A runOnce deployment job's steps are the union of its lifecycle hooks in fixed order** (`preDeploy → deploy → routeTraffic → postRouteTraffic → onFailure → onSuccess`, C-E04-146), flattened into one `steps/` directory with the hook recorded per step so E08 can recover the grouping; `rolling`/`canary` jobs carry no steps (they are a bare marker, E04-S03-T03).

    One further rule, also internal: **a shorthand-desugared step (`checkout`/`download`/`publish`, C-E04-031) names its file after the recovered `origin` keyword plus the input that distinguishes it** (`checkout-self`, `download-current`, `publish-drop`) rather than after its displayName — the builder defaults that displayName to the bare GUID, and `010-6d15af64-….sh` is not navigable. The guard is `displayName === task.name`, so an *authored* `displayName:` still wins.

    (a) **`--only-stage` drops a dependency on a stage it left out, and warns.** The three candidates were refuse, drop-and-warn, and keep-silently. The runtime's `azdo__task_handler` still resolves a `PowerShell3` handler exactly as before — its preference order mirrors the agent's (C-E07-006) and a lower-level primitive should not grow policy. `disposeStep` is the module whose whole job is "how does this task run here?", so the refusal belongs there, where it becomes a stub *with a warning naming the mechanism* instead of a wall of red text at run time. Implementing real `PowerShell3` support (importing the SDK, satisfying its environment expectations) is E07 architecture and is not attempted here.

83. **`auth login` reports which mode works; it does not cache a token, and `--github` moved to `status` (2026-09-04, E10-S03-T01).** The surface in §1 promised `auth login [--github] … [--mode interactive|az|pat]` and the command's own description said "sign in and cache a refresh token". Building it revealed that two of those clauses describe surfaces that do not exist, and they are *different* failures:

    (a) **Caching is not possible, and for the working arm not desirable.** `AzureCredentialStore.save()` has no production caller anywhere in the repository (C-E10-030/031): the only arm that would write it is the device-code flow, which is E09-S01-T01 and unbuilt. The `az` arm reuses a session `az login` created; the `pat` arm reads an environment variable, and writing *that* to disk would persist a secret the user deliberately kept in their environment — a decision the tool has no business taking for them. `login`'s honest job is select → probe → report, and its description now says so.

    (b) **`--github` on `login` is an invented surface; on `status` it is real.** `resolveGitHubCredential` has three arms — `gh-cli`, `env`, `anonymous` — and `github.ts`'s header records that the OAuth device flow is "deferred there until demand" (C-E10-033). There is nothing to sign in *to*, so `auth login --github` is refused with what to do instead, while `auth status --github` reports which arm supplied the credential. `anonymous` is a working state (public templates resolve without a token) and never fails the command.

    (c) **`--mode interactive` is deferred, not wrong.** The Azure DevOps device-code flow is grounded end to end (C-E09-001..006) and blocked only on a human at a browser. The command refuses it by naming E09-S01-T01 rather than rendering a code no arm will mint. This is the one clause that will simply start working.

    (d) **The Do field's spinner has nothing to spin for** (C-E10-034). Device-code polling is the only operation that would justify one. Every other call is a single request, so "non-TTY behaviour" here is the *absence* of terminal-dependent output rather than a fallback for it: plain lines and no ANSI on a TTY or off it, asserted by testing that neither stream contains an escape byte. The work a spinner would not do is done by the stream split — the table on stdout so `auth status | grep mode` keeps working, the verdict on stderr through the CLI's one error path.

84. **`auth status` probes past the first refusal, and reports the working mode as an instruction rather than applying it (2026-09-04, E10-S03-T01).** Measured on the test organization (C-E10-032): `AUTH_MODE_ORDER` is `interactive → az → pat`, so an existing `az` session wins selection, and on that Microsoft-account-backed organization the token is rejected with HTTP 302 while the `AZDO_PAT` in the same shell returns 200 on the same URL seconds later. A status command that reported only the refusal would tell a user who *can* authenticate that they cannot.

    So on a rejection the command probes the remaining modes and, when one authenticates, prints `works --mode pat …` and makes that the hint. It deliberately does **not** change what selection returns: `convert` uses `selectAzureCredential`'s answer, and a status command that reported a different mode would disagree with the tool it exists to explain. The gap this exposes — that the auto chain has no way to prefer an arm the organization will actually accept — is E09's to close, and is named here rather than papered over.
