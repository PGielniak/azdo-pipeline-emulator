# 06 — CLI & config, testing strategy, detailed roadmap

## 1. CLI

```
azdo-emu auth login [--github] [--org URL] [--mode interactive|az|pat]
azdo-emu auth status

azdo-emu convert <pipeline.yml> -o <dir>
    [--org URL --project NAME]            # context for @alias resolution, variable groups, schema
    [--parameter key=value]...            # runtime parameters (repeatable); complex via @file.json
    [--target-os linux|windows|macos]     # override pool inference
    [--checkout-mode clone|copy|worktree]
    [--exec-env auto|sandbox|host]        # D11: default execution environment baked into the project (docs/04 §9)
    [--sandbox-image IMG]                 # override the default vmImage→image mapping
    [--group-names | --no-group-names]    # list variable-group names in .env.example when signed in (values never fetched)
    [--min-coverage <pct>]                # exit 3 if the coverage report (docs/04 §13) is below threshold
    [--frozen | --update [what]]          # lockfile behavior (docs/05 §4)
    [--offline]
    [--only-stage NAME]...                # partial conversion for huge pipelines

azdo-emu doctor <outdir> [--sandbox]      # verify tool prereqs from manifest.json — on the host, or inside the sandbox image (D11)
azdo-emu fetch-artifacts <outdir> [--refresh|--latest]
azdo-emu preview-diff <pipeline.yml>      # dev/CI parity check vs the real service (docs/02 §8)
azdo-emu run <outdir> [...]               # thin convenience proxy to <outdir>/run.sh (optional sugar)
```

Conventions: human-readable output with `--json` for tooling; exit codes 0 ok / 1 conversion errors / 2 warnings-as-errors (`--strict`) / 3 below `--min-coverage`. **CLI usage errors** (unknown flag, missing argument, unknown command) reuse **1** rather than adding a code outside that set — which is also the CLI library's own default, so the two never need translating (E13-S01-T01, C-E13-007). `convert` always ends with the coverage one-liner (docs/04 §13).

Implemented in `packages/cli` (E13-S01-T01): `src/exit.ts` owns the policy (`EXIT`, `CliError`, `NotImplementedError`), `src/program.ts` registers the surface above and returns an exit code instead of calling `process.exit`, and `src/bin.ts` is the only module that touches process state. Commands not yet implemented are *registered* and fail with a message naming the epic that implements them, so `--help` stays honest about the intended surface.

## 2. Config file — `azdo-emu.yaml` (next to the pipeline, all keys optional; CLI > config > defaults)

```yaml
organization: https://dev.azure.com/contoso
project: Platform
auth: { azdo: interactive, github: gh }          # interactive|az|pat / gh|pat
parameters: { deployEnv: dev }                    # default runtime parameters
repositories:                                     # alias overrides (docs/05 §3)
  templates: { path: ../pipeline-templates }      #   e.g. local working copy while editing templates
variableGroups: { listNames: true }               # names only — values are always user-filled in .env
coverage: { min: 0 }                              # optional convert gate (0 = report-only)
tasks:
  unknown: stub                                   # stub|fail|prompt
  overrides: { "SonarQubePrepare@5": skip }       # per-task: skip|stub|fail
  execute: []                                     # P6 high-fidelity list, e.g. ["Npm@1"]
output:
  targetOs: linux
  checkoutMode: clone
  sharedWorkspace: false
  execution:                                      # D11 sandbox (docs/04 §9)
    environment: auto                             #   auto|sandbox|host — auto = sandbox when docker/podman present
    image: null                                   #   override the default vmImage→image mapping
    dockerSocket: auto                            #   auto|share|none — host-socket passthrough for docker-using pipelines
```

Implemented in `packages/cli/src/config/` (E13-S01-T02): discovery is **beside the pipeline file** (there is no `--config` flag in §1); parsing uses plain `yaml`, *not* the engine's pipeline parser, so the service quirks (anchors rejected, case-folded duplicate keys, single document — C-E01-021..028) deliberately do **not** apply to our own file format. Two rules §2 leaves open are settled in `research/E13-cli-config-doctor.md`: **map-valued keys merge per key** (`parameters`, `repositories`, `tasks.overrides`) while scalars and lists replace wholesale (C-E13-012), and **paths typed on the command line resolve from the working directory while paths written in the config resolve from the config file's own directory** (C-E13-013). The machine-readable schema is committed at `schema/azdo-emu.schema.json` (draft-07) for editor support via `# yaml-language-server: $schema=…`; a test pins it to the loader so the two cannot drift.

## 3. Testing strategy

| Layer | What | How |
|---|---|---|
| L1 Expression unit | Full function/coercion table (~300 cases from the expressions doc + oracle-resolved edge cases) | Table-driven; same tables run against **both** backends (eval + compiled-shell via bats) so the two can never diverge |
| L2 Expansion goldens | Fixture YAML in → expanded YAML out | Snapshot tests; fixtures include every directive, template type, parameter type, nesting patterns |
| L3 **Server oracle** | Our expansion ≡ service `finalYaml` | `preview-diff` over the corpus against a dedicated test org (PAT in CI secret), nightly + pre-release gate; every discovered divergence becomes a permanent L2 fixture |
| L4 Runtime unit | `runtime.sh` behaviors: setvariable/isoutput propagation, prependpath, masking, macro edge cases (unmatched literal), conditions vs results, continueOnError/failOnStderr/retries, artifact flow, deps outputs across jobs/stages | bats-core; runs in CI on ubuntu + macos |
| L5 E2E | Convert & run sample apps (dotnet, node, python, docker) in containers approximating hosted images | Docker; assert artifacts produced, exit codes, key log lines |
| L6 Real-run parity spot checks | Same fixture pipeline run in real ADO and locally; compare artifact contents, produced variables, step result sequence | Manual-triggered CI job (costs real pipeline minutes); release gate for majors |

Repo layout of the runners (E12-S01-T01): L1/L2 run under **vitest projects** — one per TypeScript package (`cli`, `engine`, `emit`, `fetch`), plus `repo` for meta-tests about the test layout itself; each project keeps its suite in `packages/<pkg>/test/**/*.test.ts`, so `pnpm vitest run --project engine` runs one package. L4 runs under **bats** in `packages/runtime/test/`, with shared helpers in `test/helpers/*.bash` loaded via `load` (relative to the test file, no `BATS_LIB_PATH` to set) and a fixture store that copies `fixtures/runtime/<name>` into the test's own `BATS_TEST_TMPDIR` before the test may touch it. `pnpm test` = vitest (with coverage) + bats; CI runs the same two commands and uploads junit + coverage reports.

Coverage gating: thresholds live in the root `vitest.config.ts` (coverage is root-level in vitest — there is no per-project coverage config); "per package" is expressed as glob keys (`packages/cli/src/**`) plus a repo-wide floor, and the numbers are a **ratchet seeded from measured coverage**, never an aspiration — a threshold above reality would make the first CI run red for no defect. Global and per-package sets are checked independently, so a package number below the repo floor is a second, narrower gate rather than a weakening; the one legitimate way a number goes *down* is re-seeding a placeholder package from measurement once it gains real code (`emit` at P2). Two traps are guarded by `test/test-layout.test.ts` rather than by convention: a package that gains tests but no project (its suite silently never runs) and a threshold glob that stops matching (vitest reports *no* error for an unmatched glob — it just stops gating).

Corpus: ≥30 pipelines patterned after real-world shapes — nested cross-repo templates, `extends` + `each` over `jobList`, matrix builds, deployment jobs with runOnce/canary, multi-checkout, artifact hand-offs between stages, variable groups + runtime expressions, monorepo path-heavy pipelines. Grown continuously from bug reports (every bug → corpus entry first).

Corpus mechanics (E12-S01-T02): entries live at `fixtures/corpus/<entry>/` (`pipeline.yml`, optional `templates/*.yml`, a README naming what the entry exercises) and their oracle pairs at `fixtures/oracle/<entry>.final.yml`, with `MANIFEST.json` recording the input hash each pair was fetched for — so a fixture edited without re-verification is a red test (`test/corpus.test.ts`), not a stale golden. `fixtures/corpus/` **mirrors the oracle repository's `/corpus/` directory**, because the service resolves `template:` references against the repo, treating a `yamlOverride` as though it were the pipeline definition's own file: templates must be pushed before the preview call, root references spelled `/corpus/<entry>/…` and in-template references spelled as bare siblings (C-E12-011/012). Goldens are redacted, so every consumer of a fresh response — the `--update` flow, the nightly `preview-diff` — must redact before diffing.

Two limits of the oracle as an instrument, found by authoring corpus v1 and load-bearing for what L2/L3 may claim:

- **The oracle cannot see everything.** `strategy: matrix`/`parallel` is *not* expanded by the service (C-E12-018) — job multiplication happens at run time — so no golden can prove it; that behaviour is E04's, verified at L6. Variable-group contents are likewise never inlined (C-E12-016), which is independent confirmation of D5.
- **Some corpus shapes need org objects, not just YAML.** `environment:` and `- group:` are validated at *load* time and fail with "does not exist or has not been authorized" until the object exists **and** the pipeline is authorized for it (C-E12-015/017); `scripts/oracle-provision.ts` provisions the ones corpus v1 needs. The expansion also rewrites shortcut steps to task **GUIDs** (`checkout`/`download` GUIDs that the task catalogue itself cannot resolve — C-E12-019/020), which the E03-S05-T01 normalizer must canonicalize or `preview-diff` reports permanent false drift.

## 5. Decisions record & remaining open questions

Decided 2026-07-30 (with the user):
1. **Azure DevOps Server (on-prem): out of scope.**
2. **Task priority = the Azure/Kubernetes deployment set** — AzurePowerShell, PowerShell/Bash, Helm install/deploy, Docker build/push, Azure resource-group (ARM/Bicep) deployment, Kubernetes actions, Key Vault, storage-account operations → group D moved to P4, general toolchains to P5 (docs/03).
3. **Windows host: skipped for now, must remain addable** — emitter keeps a per-job target-OS backend seam; scheduled as the "Future" phase.
4. **Variable groups → `.env.example` only**, filled by the user (names listed when signed in; values never fetched).
5. **Every conversion emits a coverage report** (docs/04 §13) with the `--min-coverage` gate.
6. **Grounding-source correction (2026-07-30, E00-S02-T02):** the C# expressions/object-templating engine sources are **not** in `microsoft/azure-pipelines-agent` (it consumes the closed `Microsoft.TeamFoundation.DistributedTask.Expressions` NuGet; conditions evaluated in `src/Agent.Worker/ExpressionManager.cs`). Open behavioral reference for E02/E03 is the `actions/runner` fork `src/Sdk/DTExpressions2`/`DTObjectTemplating`/`DTPipelines`, with the oracle (D6) outranking it on divergence. Corrected: PLAN §9, docs/02 intro, E02/E03 epic grounding sets, REFERENCES.md (claims C-E00-012/013).
7. **Isolated execution by default (D11)** — decided 2026-07-30 (user requirement: local debugging must run in a container-isolated environment): the generated project executes inside one long-lived sandbox container per run when a container runtime is available (`auto`; `--host` opts out), project bind-mounted at the identical absolute path so the same scripts run unchanged in both environments (D2 intact); docker-socket passthrough is opt-in for docker-using pipelines. Distinct from ADO `container:` jobs (E14-S02). Added: PLAN §5 D11, docs/04 §9, config `output.execution.*`, story E14-S04 (T01/T02 scheduled at P2 tail).

8. **Schema validation is a guided walk, and the docs outrank the vendored schema (2026-07-30, E01-S02-T01).** The vendored `service-schema.json` is not self-sufficient: acceptance depends on the VS Code-extension keywords (`firstProperty`/`ignoreCase`/`aliases`) and on pipeline values being strings, so a stock ajv run *rejects valid pipelines* (documented `target:` on task steps) and emits >1000 errors for a single mistyped key (C-E01-011, C-E01-019). Decided: implement the walk in `packages/engine/src/frontend/validate.ts` mirroring `microsoft/azure-pipelines-language-server` semantics; keep ajv only as the vendored-file integrity smoke test; carry doc-proven schema fixes as an explicit `DOCUMENTED_CORRECTIONS` list re-checked on every schema refresh; treat unknown tasks/inputs as warnings until the org schema lands (E01-S02-T03). Two behaviors are oracle-pending in `research/E01-yaml-frontend.md` (Q1 discriminator ordering — warning for now; Q2 unknown task inputs). Updated: docs/01 §1.

9. **Doc correction — `---` is a marker, not always a separator (2026-08-11, E01-S01-T02).** docs/01 §1 said "Only a single document per file; `---` separators rejected". The live service accepts a single document opened by a leading `---` and closed by a trailing `...` (both HTTP 200), and rejects only a *second* document (C-E01-025/024); reading the old wording literally would have produced false rejections on the very common `---`-prefixed pipeline file. Also corrected in the same pass: anchors are rejected on the **definition**, not on alias use, so the placeholder `ALIAS_UNSUPPORTED` error from E01-S01-T01 is replaced by `ANCHOR_UNSUPPORTED` (C-E01-022), and duplicate keys are reported at the second occurrence with the service's own wording and collide **case-insensitively even for user-chosen names** (C-E01-023/028) — the yaml package's `uniqueKeys` check is therefore turned off so our check owns the message. Updated: docs/01 §1; evidence `research/experiments/E01-quirks/`.

10. **The org schema replaces the vendored one wholesale, and falls back rather than failing (2026-08-11, E01-S02-T03).** The measured live `GET {org}/_apis/distributedtask/yamlschema` response is the *same generator's* document as the vendored snapshot (draft-07, same `$id`, all four VS Code keywords, identical 119 definitions; the one non-task divergence resolves to the same `{type: string}`) — so injection is a swap, not a merge, and nothing the walk relies on is lost (C-E01-030/032). Decided: gate an injected document on dialect + "uses no keyword the walk leaves unimplemented", and on failure **degrade to the vendored schema with recorded reasons** instead of erroring, since a surprising server response must not block a conversion; apply `DOCUMENTED_CORRECTIONS` to the org document too, because they patch the generator rather than our snapshot (C-E01-037); word the unknown-task hint by source, mirroring the service's own `validateTaskNames` semantics (C-E01-033). Fetch/cache stays E08-S03-T07, now with a measured cache policy (no bustable version, non-byte-stable body, `vso.agentpools` scope — C-E01-034/035/036). Updated: docs/01 §1, docs/05 §2 + §4; evidence `research/experiments/E01-orgschema/`.

11. **CLI library = commander 15, and `packages/cli` alone raises the Node floor to ≥22.12 (2026-08-11, E13-S01-T01).** clipanion's current release is a pre-release (`4.0.0-rc.4`), so commander is the stable choice (C-E13-001). commander 15 declares `node >=22.12.0`, above this repo's `>=22`; C-E00-002 requires a decision entry for a floor raise, so: raised **only for `packages/cli`**, the package that depends on it, since 22.12.0 is the first 22.x of the LTS line and excludes nothing supported (C-E13-002). Also decided here: CLI usage errors reuse exit 1 (docs/06 §1 above, C-E13-007), and `--help`/`--version` reach our exit path as `CommanderError` with code 0, so the policy maps by `exitCode` and never by "an error was thrown" (C-E13-005).

12. **The expression grammar is the *service's*, not the `actions/runner` fork's (2026-08-11, E02-S01-T01).** E02's grounding set names `actions/runner` `src/Sdk/DTExpressions2` as the open reference (C-E00-012/013), but that fork is the **GitHub Actions** dialect: infix operators, ordinal `true`/`false`/`null` keywords, Actions' function set. 74 live preview probes settled the Azure Pipelines grammar against it (`research/experiments/E02-grammar/survey.md`), and the divergences are not cosmetic: Azure Pipelines has **no operators at all** — `==`, `!=`, `<`, `>`, `&&`, `||`, `!` and parenthesised grouping are all rejected, so the parser is `primary postfix*` with no precedence climbing (C-E02-001); booleans are case-**in**sensitive (C-E02-002); `null`, `NaN`, `Infinity`, `+1`, `1e3`, `0x1F` are not literals (C-E02-003/004); a Version is 3–4 segments, so `1.2` is a Number (C-E02-005, docs/02 §6 corrected); and the depth ceiling of 50 counts function arguments only, member-access chains being free (C-E02-014). Decided: the fork is used for *shape* only (token kinds, legality-by-previous-token, the `''` escape loop) and every accept/reject rule is decided by probe, D6 breaking ties; function/context **name and arity resolution is injected** (`ExprRegistry`) rather than built in, so E02-S03/S04 own the semantics and a syntax-only parse stays possible; and the unverified `MaxLength = 21000` from the fork is deliberately **not** implemented (an unverified ceiling would reject pipelines the service runs) — open for E03's server-limit work. Updated: docs/02 §6; evidence `research/E02-expressions.md`.

13. **Expression conversion follows the live service where Learn's prose is stale (2026-08-12, E02-S02-T02).** The Learn table is correct about direction and supported cells, but its String→Number prose says `Int32.TryParse`; live preview accepts both `'0.5'` and `'1,000'` as Numbers (C-E02-021). Also, the 3–4 segment rule applies to Version *literals* only: String/Number conversion produces 2-segment Versions, with missing Build distinct from zero (C-E02-022). Decided: preserve the literal parser rule, widen the evaluator's Version invariant to 2–4, implement invariant decimal/grouped String→Number conversion, and let D6's oracle hierarchy override the stale prose. Updated: docs/02 §6; evidence `research/experiments/E02-coercion/`.

14. **Expression Object values carry their key comparer (2026-08-12, E02-S02-T03).** The backlog's "case-insensitivity (verify!)" is not global: live preview proves nested parameter objects use ordinal case-sensitive lookup while variables use ordinal-ignore-case, matching the fork's two distinct dictionary context classes (C-E02-027). Decided: `ExprObject` stores `ordinal` or `ordinalIgnoreCase`; context construction chooses it, while property and index syntax share one null-propagating access operation. Updated: docs/02 §6; evidence `research/experiments/E02-members/`.

15. **Expression errors: the service's sentence verbatim, our own coordinates (2026-08-12, E02-S01-T02).** 64 further live rejections (`research/experiments/E02-errors/`) settled how a rejection is *rendered*, and four of the answers are things we deliberately do not copy. (a) `(Line, Col)` locates the **host scalar**, never the offending token (C-E02-105) — we range the token so the code frame carets it, and keep the service's `Located at position N within expression` in the message, so the two remain reconcilable. (b) An expression embedded in a larger scalar is reported against a synthetic `format(…)` call the service compiles the scalar into (C-E02-109); that text is in no file the user owns, so we report their expression instead — and the finding is handed to E03-S01-T05 as evidence for interpolation. (c) Compile-time messages are truncated at 500 characters, mid-URL if need be (C-E02-107); we do not truncate, and the parity test truncates *ours* to prove equality. (d) The one runtime/compile-time **kind** swap (C-E02-015) is not reproduced: one grammar, one kind. Two findings changed the parser rather than the renderer: `!` is keyword-shaped, not a symbol (C-E02-101), and name resolution is **deferred** behind the syntax parse while arity is not (C-E02-103) — together these close the `! true` divergence E02-S01-T01 left open, and reclassify `+1`/`"double"`/`!true` as names that fail to resolve rather than lexical errors (C-E02-102). Updated: docs/02 §3 + §6; evidence `research/E02-expressions.md` C-E02-101..110.

16. **The general-function backlog follows the current Learn catalogue (2026-08-12, E02-S03-T02).** The story requires every documented function, but its task split omitted `startsWith`, `endsWith`, and the now-documented `xor`; docs/02's function list also omitted `xor` (C-E02-040). Decided: supersede the incomplete T02 without silently widening it, add corrected E02-S03-T04 at the end of the story, and re-sync the docs list. This is catalogue drift/bookkeeping, not a semantic choice; each function still requires its own grounding before implementation.

17. **Step-level status-function arity is enforced at convert time, against a service that accepts it (2026-08-12, E02-S03-T03).** The agent registers `always/canceled/failed/succeeded/succeededOrFailed` with `minParameters: 0, maxParameters: 0` (C-E02-061), so `condition: succeeded('A')` on a *step* fails at run time. The service does not catch it: a step condition is validated by a permissive path that resolves no function names at all — `nosuchfunc(1, 2, 3)` and a bare `always` are both accepted with HTTP 200, while the same `nosuchfunc()` on a job or stage is rejected — and step rejections arrive wrapped in `Job <j>: Step <s> specifies condition <c> which is not valid. Reason: …` where job/stage rejections carry the bare message (C-E02-060). Decided: the signature table is a function of scope, and we **reject at convert time what preview accepts**, because the alternative is emitting a pipeline that converts locally and dies on the agent. Corollary recorded with it: "the service accepted it in a step condition" is not evidence that a step condition may contain it, so no later task may use a step-slot 200 as grounding. Updated: docs/02 §6; evidence `research/experiments/E02-status/survey.md`, `research/E02-expressions.md` C-E02-060..072.

18. **General-function arities follow the live parser where Learn is stale (2026-08-12, E02-S03-T04).** Thirty preview probes established two actionable catalogue contradictions: Learn says `iif` has minimum 1 / maximum 3, but the service rejects one and two arguments and accepts exactly three; it also evaluates the unselected branch, so this function is eager. Learn says `counter` takes `prefix, seed`, but the runtime-variable parser accepts one or two arguments; E02 therefore exposes the accepted one-argument form while passing an absent seed to the injected state provider, leaving any default policy to E06 rather than guessing it. Also recorded: `length(Object)` returns the property count and `split` uses one exact delimiter string. Updated: docs/02 §6; evidence `research/E02-expressions.md` C-E02-041..051 and `research/experiments/E02-general/`.

**2026-08-12 (E02-S01-T03) — Decision-record amendment.** Bare known functions are a seventh parse-error shape. The lexer intentionally classifies a bare `eq` as a generic named-value token because it only knows it is a call when `(` follows; per-slot registry lookup separates it from a bare legal context. Live preview shows a registered `eq` emits `Expected '(' to follow a function: 'eq'` in both `${{ }}` and a job `condition:`, while `always` outside a status-function slot stays `Unrecognized value` and bare `variables` evaluates as a mapping before schema validation rejects it (C-E02-132..134). Decided: preserve the shared lexer, add `expected-function-call` only for an available function name, and defer it so a later syntax error retains the parser's established precedence. This amends decision 19's historical six-shape count to seven; evidence `research/experiments/E02-bare-functions/`.

Still open:
1. Distribution: npm global install acceptable, or single static binary required?
2. Should `coverage.min` have an opinionated default (e.g. warn under 60%), or stay report-only until asked?

19. **Expression context availability is gated per *slot*, and two slots are evidence-free (2026-08-12, E02-S04-T01).** 61 preview probes (`research/experiments/E02-context/survey.md`) measured seven contexts against five slots and found **three** distinct name tables where Learn describes a compile-time/runtime binary: `${{ }}`+`${{ if }}` → `parameters`/`variables`; root `$[ ]` variable → `variables`/`resources`/`pipeline`; job or stage `condition:` → `variables`/`dependencies`/`stageDependencies`/`pipeline`. `resources` and `dependencies` dissociate doubly across the two runtime slots, so no phase model reproduces the gate — `ExprSlot` does. Decided: (a) availability is implemented as a per-slot `namedValues` set fed to `parseExpression`, and **no new error kind is added**, because a wrong-slot context is rejected byte-identically to a nonexistent one (C-E02-081); (b) the same `ExprSlot` derives the status-function scope, so the context table and the function table cannot be paired inconsistently; (c) `parameters` gets an explicit miss policy of `error` in the value model — the service raises `Key not found 'x'` there while returning Null for the identical miss on `variables` (C-E02-087), and that error is an **evaluation** error, deliberately not folded into `ExprErrorCode`/`errors.ts`, whose six shapes are all parse failures (C-E02-088). Corollary extending decision 17: a **job-scoped `variables:` value** is a second permissive slot — it accepts `$[ nosuchcontext.probe ]` and the bad-arity `$[ eq(1) ]` — so like a step condition it yields no grounding, and an earlier reading of this survey that had `dependencies`/`parameters` "becoming available inside a job" was an artifact caught only by adding negative controls (C-E02-085). The same slot key gates functions in both directions: `counter` is restricted to the runtime-variable slot via `SLOT_RESTRICTED_FUNCTIONS`, because the service rejects it in job/stage conditions *and* in a compile-time variable definition — narrower than the doc sentence, and a case where handing every slot the full non-status function set would have accepted what the service refuses (C-E02-096). Open cell handed on: the deployment-scoped variable slot for `environment` could not be measured (the test org has no such environment; both probe and control failed on it) — E02-S04-T03/E10 owns it. Updated: docs/02 §6 Contexts; evidence `research/E02-expressions.md` C-E02-080..091.

20. **`resources.pipeline.<alias>.*` is a *variable* family, not a member of the `resources` context (2026-08-12, E02-S04-T03).** Learn documents twelve pipeline-resource fields written as paths (`resources.pipeline.<Alias>.runID`) and calls them "predefined variables"; the sibling repository family is documented with the same spelling *and* a `$[ resources.repositories.common.ref ]` example, which makes "these are context members" the natural reading. Two real runs (`research/experiments/E02-resources/real-run.md`) measured it false: with the metadata demonstrably present in the run, the chain `resources.pipeline.probe.runID` returns **empty** while `variables['resources.pipeline.probe.runID']` and `$(resources.pipeline.probe.runID)` both return the run id, and `convertToJson(resources)` dumps only `{"repositories": …, "containers": …}` (C-E02-120/121). The two families are mirror images: repository metadata is context-only and absent from `variables[…]` (C-E02-125). Decided: (a) two builders in `packages/engine/src/expr/resources.ts` — `resourcesContext()` for the real context and `pipelineResourceVariables()` for the flat dotted entries, the latter returned as its own labelled map rather than pre-merged into `variablesContext`, because the resource variables are runtime-only and must not reach the compile-time table; (b) `projectName` is modelled as **key absence**, since through an expression absence and empty are indistinguishable and only the emitter's env export can tell them apart (C-E02-122); (c) env names upper-case with `.` → `_` and **hyphens preserved** — the alias charset allows `-` and the doc's own sample is `RESOURCES_PIPELINE_OTHER-PROJECT-PIPELINE_PROJECTNAME` (C-E02-127). Consequence worth carrying into E03/E04: a job or stage `condition:` cannot name `resources` (C-E02-082) but *can* read the same metadata through `variables[…]`, verified by a live job whose condition did exactly that. Open cell **re-handed, not closed**: decision 19 left the deployment-scoped variable slot for `environment` to "E02-S04-T03/E10"; this task measured `resources`, not `environment`, so the cell now belongs to **E10** (deployment strategies), which is where an environment the test org actually has will exist. Updated: docs/02 §6 Contexts, docs/05 §4 lockfile `pipelines` entry; evidence `research/E02-expressions.md` C-E02-120..127, which supersede the doc-only C-E02-111/112.

22. **Template directive *recognition* is a closed, case-sensitive keyword set whose parameters are expression tokens, and the walker executes nothing (2026-08-12, E03-S01-T01).** 33 preview probes (`research/experiments/E03-walk/`) measured the rules neither the templates doc nor the template-expressions doc states, and two of the answers invert the natural guess. (a) **Keywords are case-sensitive, lower-case only** — `${{ IF … }}`/`${{ EACH … }}`/`${{ INSERT }}` are not mis-spelled directives but *not directives at all*, falling through to ordinary expression parsing (C-E03-100). This is the only case-sensitive corner of the language, and it sits directly beside a case-**in**sensitive one: loop-variable names fold case (C-E03-107). (b) **Directive parameters are top-level expression units, not whitespace-split words** — `eq(1, 1)` is one, pinned by "Exactly 0 parameter(s) were expected following the directive 'else'. Actual parameter count: 2" for `${{ else if eq(1, 1) }}` (C-E03-101). Decided: the directive text is tokenized with E02's lexer and units read off bracket depth 0 — **never** `indexOf(' in ')`, because `${{ each item in split('a in b', ' in ') }}` legitimately iterates `a`,`b` and a text search picks the wrong separator *silently*, with no error to notice (C-E03-104). (c) `each`'s loop variable shares one **flat namespace with the contexts** and collides rather than shadowing — "The idenfifier 'variables' has already been defined within the current scope", the service's own typo (C-E03-106) — so `bindLoopVariable` returns a rejection instead of a nested scope. (d) **Docs correction, rule 5:** the template-expressions doc's "Expressions are only expanded for `stages`, `jobs`, `steps`, and `containers` … You can't … use an expression inside `trigger`" is false — `trigger: [${{ 'main' }}]` and `pool.demands` both expand (C-E03-109). Real position-sensitivity exists but has exactly **one** measured member, `resources.repositories`, with its own sentence `A template expression is not allowed in this context`, so it is modelled as a seam rather than a table extrapolated from the doc's list (C-E03-110). (e) **Scope line held:** T01 detects directives, frames names and accumulates diagnostics; `if`/`each`/`insert` *semantics* stay with E03-S01-T02/T03/T04, each of which must land its own oracle fixture pairs — executing them here would ship directive behavior without the grounding those tasks mandate. Two findings handed on rather than fixed: our C-E01-023 duplicate-key quirk rejects two byte-identical `${{ if }}` keys that the service accepts and merges (C-E03-111 → new task **E01-S01-T04**; E01-S01-T02 is done and its 13 transcripts simply never probed a `${{ }}` key), and `Expected '(' to follow a function: '<name>'` is a general expression error kind absent from `ExprErrorCode`, so a bare `${{ eq }}` renders as `Unrecognized value` where the service names the missing paren (C-E03-114 → E02-S01). Updated: docs/02 §4; evidence `research/E03-template-engine.md` C-E03-100..115.

23. **The shell backend is verified by execution, and three divergences are declared rather than discovered (2026-08-13, E02-S05-T02).** The harness required by this task turned out to be the first thing that ever *ran* compiled output, and it immediately falsified E02-S05-T01's premise: comparisons had been mapped onto `test` operators, which discards the operand kind the conversion table depends on (`eq(1, true)` is True by Boolean→Number and `[ "1" = True ]` is silently False), status functions compiled to a bare word compared against `True` so the function was never invoked, and every emitted `azdo_expr_*` helper had no definition because `packages/runtime/lib/expr.sh` — named in T01's own **Do** — did not exist (C-E02-145). None of that is visible to a test that asserts the emitted *string*, which is what T01 shipped. Decided: (a) values cross into the shell as their **String form plus a kind tag** (`bool | num | str | ver`) and `azdo_expr_cmp` reproduces `compareValues()` in bash; (b) the predicate status convention is **0 True / 1 False / 2 evaluation error**, because `test` already reserves >1 for errors and a missing helper exits 127, so a harness reading "non-zero = False" would pass over a backend that never ran (C-E02-135/136); (c) every string operation pins `LC_ALL=C`, since `[[ < ]]` and `${v^^}` are locale-collated — `alpha < BETA` flips between the C and UTF-8 locales (C-E02-142); (d) rows the shell cannot express raise `BashCompileError` at convert time, and the measured set is Object/Array plus `split`/`join`/`convertToJson`/`containsValue`/dynamic index/`counter` (C-E02-139). Three **declared divergences** are pinned as rows carrying the measured shell answer, so each is red if it widens *or* if it quietly goes away: no Null, so an ordered comparison against a missing variable answers instead of raising (C-E02-138); an evaluation error is masked by `||` and discarded outright in value position, because command substitution keeps output and not status (C-E02-143/144); and non-ASCII case folding differs from .NET OrdinalIgnoreCase (C-E02-141). The error-propagation pair is handed to **E06-S03-T03**, which owns condition evaluation, rather than fixed here — a status-preserving protocol is a runtime contract, not a compiler detail. Structural finding handed on: T02 says the tables run "through both the evaluator and the compiled bash", but **E02 has no AST evaluator** — the tables call `compareValues`/`evaluateLogicalMembershipFunction`/`evaluateGeneralFunction` directly and no task ever allocated a walker; building one inside a harness task would have buried a missing story, so it is filed as new task **E02-S05-T03** and the rows carry an explicit `evaluate()` thunk in the meantime. Updated: docs/02 §6; evidence `research/E02-expressions.md` C-E02-135..146, `research/experiments/E02-conformance/shell-semantics.md`, `packages/runtime/test/expr-conformance.bats` (104 executed rows).

27. **Conditional chains are container-stateful but emit at each winning directive's own position (2026-08-19, E03-S01-T02; merge-reconciled 2026-08-19).** The task's **Do** field says "chain grouping in document order; winning branch spliced into parent", which can be misread as collecting a contiguous run and emitting at the head. Two independent live matrices — 45 probes and 37 successful pairs — refute that reading. The winner remains at its **own** position: with a false `if`, the intervening step precedes the `else` body (C-E03-128). Conditions evaluate in document order and stop at the first winner, so `if(true) / elseif parameters.missing / else` expands without touching the raising member (C-E03-132/134). The parallel implementations both encoded those rules, but only the per-container forward state machine in `conditionals.ts` matched the full fixture union: the backwards-scan implementation rejected Array/Object conditions and a Mapping body in sequence position, finishing 34/37 versus 37/37. Conditional truthiness covers every value kind, including truthy empty Array/Object (C-E03-135), and structural body handling distinguishes sequence flattening, mapping-as-item, mapping merge, and invalid mapping-parent shapes (C-E03-136). Losing clauses remain silent; orphans, clauses after `else`, and duplicate `else` are measured errors (C-E03-129/130/137).
